# Mini Pi Plus Pro 实机验证与限时巡线

## 2026-11-11：共享导航入口

当前 `shadow.py` 已委托给共享导航实现，完整巡线、避障、终点和 AMP 输入适配均在 `navigation/`。
安装、版本校验、旁路输出和明日接机顺序见 [共享导航部署说明](SHARED_NAVIGATION.md)。
下面的直线/停走转向试验与旧输出格式属于历史实现，不能当作共享导航已完成实机验证。


`shadow.py` 是独立观察程序，不包含 ROS Publisher、电机控制、模式切换或手柄注入。
它不修改原厂 `sim2real`、自启动、AMP 策略，只能验证相机/IMU/关节反馈和算法计算。
`head_step.py` 负责已授权的头部姿态恢复；另有 `line_trial.py` 做限时实机巡线，
会经单一速度发布者向原厂 loco 发送速度指令。三者的能力和输出需分别判断。

实机已确认：Orin NX、Ubuntu 20.04、Python 3.8、ROS1 Noetic、D435i、librealsense 2.55.1。
原厂运行配置 `S-12L8A0G2H0W`，AMP 配置 20 动作、69 维观测、5 历史帧、50 Hz。
`/cmd_vel` 在最初检查时没有订阅者；恢复 Default 后已确认原厂节点订阅它，
同时接收 `/joy_msg`。之后已通过限时试验确认速度接口可驱动行走，现场用户确认机器人走动。
30 秒连续巡线仍待验证；短时走动不能作为整圈完赛证据。
巡线试验不向 `/joy_msg` 增加第二个发布者，而是在原厂手柄翻译器中仲裁速度，保留原按钮路径。

## 限时巡线与断网处理

当前源码增加了弯道恢复版本：优先按两侧白线的可见分段采样生成中心路径，
导航目标从采样路径前方 0.40 m 处读取，近段切线用于方向诊断，避免跨拐角二次曲线
向脚下外推造成虚假的大角度。视觉方向 20° 现在只记录为诊断信息。
短转后的等待为 0.5 秒，短暂丢线停止输出后自动重观测，连续三帧有效才恢复；
持续失去可信跑道 8 秒或相机断帧 2 秒才结束。15 cm 近段偏移限制、障碍、
姿态与手柄保护继续生效。上一版本和当前源码的部署状态须核对远端哈希清单。

上一轮停车帧的回放中，旧二次外推为约 20.8°、14.9 cm；分段近场拟合为约
−2.2°、−5.0 cm。这是同一记录画面的算法比较，不是新的实机位置标定。

2026-11-10 转向诊断确认：该原厂 AMP 在写入观测前先进行 0.3 系数滤波，
再将绝对值小于 0.17 的转向量清零，并将清零后的值作为下次滤波状态。
因此从静止持续输入 0.45，会持续得到 0，不能靠等待逐渐生效。
直接订阅 `/sim2real_debug_data_obs` 的第 6–8 项，已确认 0.45 被清零，
±0.65 可进入策略但实机只有少量姿态变化；±1.0 的短时试验产生了可见转向。
详细记录见 `output/deployment/line_trial_20261110/actual10_turn_observation/`、
`actual11_turn_amplitude1/`，用户现场确认后者有小幅转向。

`--calibrated-turns` 采用停走交替的实验控制：看向前方 0.55 m 的中心点，
相对方位超过 6°时停止前进、请求 ±1.0 转向，50 Hz 本机仲裁器在 IMU 测得约
6°转角或脉冲达到 1.8 秒时切断转向。视觉收到完成状态后等待 0.8 秒，再根据
新画面选择继续短转或恢复 0.4 m/s 前进。单段 20°/3 秒、姿态和手柄保护仍保留。
过时画面不产生运动指令，需要连续三帧新鲜有效观测才恢复输出；长时间断帧及失线仍结束任务。

`actual_14_imu_pulses` 日志已确认两次“纠偏后恢复前进指令”；最终因相机地面坐标中的
拟合方向达到 20.89°而停车。完整 30 秒巡线和真实位置跟踪尚未通过验证。
实际跑道宽度 50 cm 可用于尺度检查，但相机/机身完整外参和静态尺度标定仍未验证。

`line_trial.py` 使用真实 RGB-D 拟合地面和两侧白线，按局部中心线的纯追踪计算
前进和转向速度，不使用仿真真值。它以相机地面坐标计算，完整相机/机身外参仍未验证，
当前只用于有现场手柄接管的限时试验。尚未完成自主绕箱、终点识别和整圈验证。

监督进程只临时替换手柄翻译器的速度发布入口，原厂主控制器和 AMP 策略持续运行。
单独的本机 50 Hz 仲裁器检查手柄、控制状态、关节、IMU、电池和视觉指令；手柄优先，
视觉指令超过 0.2 秒未更新即输出零。视觉失效、姿态异常或任务时限到达会结束本次试验，
退出时恢复原厂手柄翻译器。无效画面不会因为 SSH 网络差而被允许继续使用。

`launch_line_trial.py` 将任务脱离 SSH 会话在机器人上运行，试验上限为 0.4 m/s、30 秒。
任务目录中的 `launch.json` 防止同一任务被重复启动，独占锁防止两个试验同时控制机器人。
SSH 确认回包丢失时，应查询或使用同一任务目录重试；不能换新目录盲目重新启动。

2026-11-10 已观察到网络延迟从十几毫秒升至约 5 秒后集中回包。远程日志读取和
文件同步采用每次最多 120 秒等待、失败后间隔 5 秒重试；身份认证拒绝及明确的远程程序
错误会停止重试。文件同步重发相同内容，并核对远端 SHA-256 清单，完整清单可用于确认
传输已完成，即使最终 SSH 退出状态回包丢失。相关工具在 `output/deployment/transport/`。
以上重试只影响远程管理，机载感知、限时和失效停车不依赖无线链路。

## 独立安装

在新建的项目目录中执行，不覆盖原厂环境：

```bash
bash deploy/install_shadow.sh
source /opt/ros/noetic/setup.bash
source /home/nvidia/sim2real/install/setup.bash
.venv/bin/python deploy/shadow.py --duration 20 --output runs/first_shadow
```

安装完成后，可直接使用 `bash deploy/run_shadow.sh 20` 重复观察测试。
安装脚本先验证原厂 NumPy/OpenCV 的基础图像处理能力，预检通过则在新虚拟环境中复用它们。
本观察程序不依赖 SciPy；姿态矩阵由四元数直接计算，已与独立参考实现对照。
预检失败时才安装 NumPy 1.24.4 / OpenCV headless 4.10.0.84；外网不稳定时，可将适配
Python 3.8 / Linux ARM64 的 wheel 和 `pip==24.3.1` 放入 `wheels/` 离线安装。

相机采集是独立 C++ 子进程：640×480 RGB 和对齐到彩色的米制深度，15 fps。
读取工厂内参和畸变，Python 中校正后降采样到 320×240。采集线程只保留最新帧；
无数据、图像积压或 IMU 无效时终止本次诊断并记录错误。退出时关闭相机子进程。
时间关联使用主机接收时刻，尚未标定传感器曝光、串口传输或 IMU 滤波时延。

## 输出解释

- `summary.json`：成功采集的帧数、处理延迟、检测到跑道的帧数及状态。
- `camera_intrinsics.json`：本次相机实际内参，不包含设备序列号。
- `telemetry.jsonl`：真实传感器诊断、关节位置、未验证的候选速度及抑制原因。
- `latest_rgb.jpg`、`latest_overlay.jpg`：相机图像和感知标记。
- `camera.log`：相机采集错误信息。

`candidate_unvalidated` 只是算法的诊断输出；`motion_output` 始终为零，并且从不发布到 ROS。
相机外参、IMU 轴对齐未校准时，识别距离、地图和候选速度都不可作为控制依据。
默认 JSON 中的外参是仿真占位值，`extrinsics_verified` 和 `imu_alignment_verified` 均为 false。
即使手动改为 true，程序也不会获得运动控制能力。

运动估计只使用 RGB-D 光流；没有套用仿真机器人的腿部 FK 模型。特征不足会明确报告
`visual_odometry_unreliable_no_fk_fallback`，不宣称已经实现可靠的真机定位。

实机用户已确认相机安装在可动头部。程序额外记录两个头部关节反馈，并明确标记
`head_camera_transform_not_calibrated`；目前尚未把头部运动纳入相机投影和视觉里程计。
首轮相机画面主要为天花板，不能视作已经检测到真实跑道。建议首版固定头部工作角度、
在该角度完成外参标定并监控角度变化；若运行时转动头部，则需完整头部运动学和逐帧外参。

若设备可枚举但没有图像帧，可先在没有其他相机使用者时显式执行一次相机复位。
2026-11-10 的部署测试中，该操作恢复了 RGB-D；这是一次恢复记录，并非长期可靠性保证。
`reset_camera.cpp` 只接受单台 D435 设备，需手动编译执行，不在安装或常规运行中自动复位。

## 进入运动测试前仍需完成

### 仅做地面平面标定

头部保持不动、绿色地面在画面中充分可见时，可运行：

```bash
source /opt/ros/noetic/setup.bash
source /home/nvidia/sim2real/install/setup.bash
.venv/bin/python deploy/calibrate_ground.py --duration 8 --output runs/ground_calibration_01
```

该程序不修改控制配置、不发布运动指令，记录真实 RGB-D、IMU 和关节数据，用多帧绿色地面
深度点做 RANSAC/SVD 拟合。输出相机离地高度、地面法向、残差、跨帧稳定性和相机到局部地面
坐标的变换。地面坐标原点为相机垂足，X 轴是相机光轴在地面上的投影，**不是机身坐标系**。
前后/左右安装偏移、相机到机身偏航、头部运动学和 IMU/机身对齐仍不可由该结果直接确定。
绿色地面不足、平面不稳定或点分布退化会报告失败，不会将原先的占位外参标成有效。

真实相机应保持在采集时的同一头部姿态。单平面结果仍需核对选中的确为地面；架上测得的
离地高度不能直接当作机器人落地行走时的相机高度。用户暂无头部机械模型/安装尺寸时，
只完成这部分测量，完整机身外参继续保持未验证。

### 用户提供的 Pro 机械模型（2026-11-10）

已解包 `PiPlusPro_SF_12L8A0G2H0W_Z_261010.zip` 到 `reference/robot/`。
模型有 22 个活动关节，头部链为
`base_link -> torso_link -> head_yaw_link -> head_pitch_link -> camera_link`。
`pro_head_model.py` 可以按 URDF 关节角计算机械相机坐标系到 base_link 的变换，
已与包内独立 MJCF 的 100 组头部姿态对照通过。它不发布指令，尚未接入 shadow 的投影。

模型的头部 pitch 范围为 `[-1.05, 0.994] rad`，原厂 PD 配置则为 `[-1.58, 1.58] rad`。
最后一次收到的 pitch 为 `1.095787525 rad`，超出该 URDF 上限约 `0.102 rad`；
需要核对实际编码器零点/方向和模型版本，不能沿用更宽的配置范围继续发指令。
`head_step.py` 现在要求读取此 URDF，在发送前同时检查两类限位；不一致时零消息退出。
这些模型与检查程序已在独立 release 目录同步并校验哈希。用户随后通过原厂手柄进入
standby，最新头部姿态回到模型范围内，之前超限的反馈作为历史记录保留。

模型中的 `camera_link` 是机械安装坐标系，未包含 RGB optical frame。
完整视觉外参仍需补充镜头光学中心/轴方向、编码器映射与 IMU/机身对齐的实测验证。
不能仅因 URDF 已导入，就将 `extrinsics_verified` 改为 true。

2026-11-10 18:08 的一次头部探测通过原厂 `/pi_plus_absolute` 发送了 38 条
仅含 `head_pitch_joint` 的小步指令；目标减少 0.04 rad，但反馈没有达到目标，程序退出。
没有发送身体关节、模式切换或保护复位指令。之后尚未完成视角调整，
旧的地面标定对应之前的头部姿态，不能用于当前相机姿态。

### Default 与头部指令的状态条件

外层 `/fsm_state = 5` 仅表示选中 Default。原厂 Default 内部还区分 INIT、standing、
standby、running 等状态。检查当前二进制确认，INIT 分支会持续对 `all` 电机组写零增益，
所以只选 Default 时，单次头部位置指令会被随后覆盖。

`head_step.py` 同时检查外层 Default 和内层 standby：内层状态使用原厂 StateInfo 消息，
并核对原厂日志中的模式切换记录；保护退出后不能继续沿用之前的 standby 记录。
运行中继续监测原厂状态、头部反馈、机身关节和 IMU。该程序只发布具名
`head_pitch_joint`，不启用站立、踏步，不发布身体关节或模式切换。

本次用户通过手柄进入 standby 后，0.04 rad 的探测已产生真实头部运动，之后按不超过
0.05 rad 的指令步幅连续下调。原厂头部 PD 存在一定静态跟踪偏差；最后一小步因偏差超过
0.025 rad 停止继续发指令。最终以停止发布后的 RGB-D 地面实测角度与多帧稳定性验收，
不以指令值直接认定相机实际俯角。没有提高增益或放宽跟踪误差检查。

最终结果保存在 `deploy/task_head_pose.json`：头部反馈 pitch 为 `0.63837 rad`（约 36.58°），
yaw 为 `0`，相机光轴实测向下 `43.9715°`。18 帧地面拟合 RMS 为 `1.606 mm`，
法向跨帧变化 P95 为 `0.03984°`；停止发布期间两个头部关节的反馈保持稳定。
当前架上姿态下，画面中心列投影到相机垂足前方约 `0.285–1.531 m` 的地面。
该范围不是相对脚掌的距离，落地后相机高度和覆盖距离也会随姿态变化。
最后一次 pitch 指令为 `0.61046 rad`，与反馈存在 `0.02791 rad` 的静差，不能把两者混用。

首次调整仅验证 Default/standby。切换到行走策略后头部是否保持此姿态仍需观察验证；
完整光学外参与 IMU 对齐未验证，自主行走输出仍未启用。

### 换电重启后的连续恢复

用户要求不分段停顿后，新增 `--restore-saved-pose`，从当前反馈角度以连续三次曲线
恢复保存的 pitch 指令，起止速度为零、峰值速度不超过 `0.1 rad/s`。
限位、反馈新鲜度、IMU 倾斜和头部跟踪检查仍有效；终点以保存的实测反馈值验收，
同时保留保存的指令值，处理已观测到的原厂 PD 静差。

`--allow-running` 仅与保存姿态恢复一起使用。它核对当前 AMP 配置和原厂 StateInfo，
要求策略恰好控制 20 个身体关节、关节名单排除头部、运行中的策略文件名一致。
running 中允许原有策略产生身体关节运动，同时继续检查全身反馈和机身倾斜。
程序没有发送身体关节、速度、手柄或模式切换指令。

本次换电后在原厂 running 状态中连续恢复成功：pitch 从 `0.02388 rad` 到
`0.63837 rad`，指令目标 `0.61046 rad`，发布结束后相机观察程序不包含运动发布者。
15 帧地面拟合得到相机向下 `38.1521°`、离当前地面 `0.59322 m`；与之前架上约 44°
的差异说明，恢复同一头部关节角不等于恢复同一世界俯角。用户确认头部已到位，
因此保持当前角度，没有继续补偿机身姿态差异。后续视觉计算应使用当前实测姿态。

### 后续机身外参与控制接入

1. 测量并验证相机到机身的外参、IMU 到机身的轴对齐；若相机安装在可动头部，接入头关节变换。
2. 接入该实机对应的运动学模型和关节偏置，验证状态量单位、方向和时序。
3. 为速度接口添加单一控制权仲裁、手柄优先、明确使能和指令/感知超时停车。
4. 在有防跌保护和现场操作人员的条件下标定速度响应，再做单箱和整圈测试。
